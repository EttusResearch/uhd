# X440 PS RFDC Block diagram

The core piece of the X440 PS RFDC block diagram is the Zynq UltraScale+ RF Data
Converter (RFDC) IP and the ARM processing system (PS). There are more
components on the block diagram, but these are not relevant for the
understanding of the clocking and data path in the block diagram, so they are
not described in this document.

This block design has to serve two use-cases.
1. X440-based operation mode where the RFDC data path clocking matches the RFNoC
   radio clock from the RF core. The RF core applies filtering to the data but
   stays within the same clock rate.

2. X410-like operation with interpolation and decimation by 3 in the RF cores,
   which introduces two different clock domains per data path in the RFDC block
   diagram. The RFDC clock is tied to the sampling rate of the RFDC block at its
   AXI interfaces.

   Through the decimation and interpolation, the data_clk will be 1/3 of the
   RFDC clock frequency. The RFNoC radio block uses the data_clk to handle the
   data. So any input signal with suffix r0 or r1 for radio_clk_0/1 from the
   radio block is using the data_clk. In the block diagram, there are some
   places where data_clk domain signals are connected to ports, which are
   expected to be driven by signals from the RFDC clock domain.

   One example is the rf_reset_controller0/rAdcResetPulse input. The core uses
   this signal in the RFClk (RFDC clock) domain, but the RFNoC radio block is
   using the data_clk domain. This connection is safe as the ratio between the
   clocks is 3 and they are synchronously generated by the MMCM in the same
   block diagram. So any pulse in the data_clk domain will be safely transferred
   to the RFClk domain and will be seen as a pulse of 3 clock cycles in the
   RFClk domain. Static timing analysis will analyze the path with the correct
   clock ratio.

   **Warning** As the data_clk is shared between both RFNoC radio blocks the
   RFDC clocks have to be aligned as well. So only a single MCR can be supported
   for both radios in this case.

## MMCM / RFDC clocking
The goal of the clock settings for the MMCM and the RFDC IP in the block diagram
is to support two main purposes:
1. A PLL reference clock (PRC) of 64 MHz.
2. Clock frequencies for all MMCM output clocks configured to be greater than
   or equal to the clock frequencies that can be configured at runtime. This
   ensures a worst-case scenario for the static timing analysis.

As the MMCM clocks are used in the block diagram and their frequency gets
checked during block diagram validation, the RFDC sampling rates have to get
aligned to the IP configuration and RFDC clock frequencies. This results in
misaligned configurations, which are only used during compilation of the bitfile
as the MMCM gets reprogrammed at runtime to support the desired sampling rates.

The 2x RFDC clocks are tied to the same clock frequency as the 1x RFDC clocks to
stay within the bounds of the MMCM output clock frequency range.

### X440-based operation
The X440-based operation allows for the maximum sampling rate of 4096 MS/s and a
maximum master clock rate (MCR) of 2048 MS/s. As the RFDC block is configured
for 8 samples per clock (SPC), the minimum required rfdc_clk frequency is 256
MHz. data_clk is configured to the same frequency as rfdc_clk but is unused in
this mode of operation.

The block diagram is saved using this configuration.

#### 400 MHz RF bandwidth
For the lower RF bandwidth of 400 MHz the RFDC clock frequencies are decimated
by 4 by overwriting the MMCM configuration for static timing analysis by
applying the constraint from file constraints/timing/x440_clocks_400.xdc.


### X410-like operation
#### 200 MHz RF bandwidth
When this configuration is needed, the constraint file
constraints/timing/x440_clocks_200.xdc applies the respective MMCM settings
using a ratio of 3:1 between rfdc_clk and data_clk to provide the correct
clocking for the decimation and interpolation.
